02 Config architecture

Single-host flake. Every module is loaded unconditionally — there are no feature flags or per-host conditionals. The flake produces exactly one system: nixosConfigurations.homeserver.

Unstable overlay

Declared inline in flake.nix. Injects selected packages from nixpkgs-unstable into the main pkgs set so any module can reference them without needing specialArgs. A package goes through the overlay when the required version isn't available in the stable channel, or when it must be taken as a pre-built binary to avoid a source compile that would exhaust RAM. Custom packages not in nixpkgs at all are defined in pkgs/ and added to the overlay the same way.

Module groups

The flake module list contains only local file paths — all external module dependencies are encapsulated inside the module that needs them. Modules are loaded in this order; the grouping determines which pkgs channel a module expects and where new modules should be inserted.

03 Config patterns

config-values.nix

NixOS options module at the repo root. Defines the homeserver namespace — single source of truth for all ports, UIDs, GIDs, shared paths, sandbox options, and the localhost address.

uids

System user IDs, grouped by service category. Services declared via services.X.enable in nixos-stable/ are not represented here — their users are created internally by the NixOS module system with no UID we need to pin. Only users we declare ourselves are pinned.

addresses / localhost

Loopback address 127.0.0.1. Used by all modules that bind a service to localhost or proxy to a localhost target — referenced in nginx.nix and every module in nixos-stable/, nixos-unstable/.

ports

All service port numbers — no port is ever hardcoded in a module. Includes internal-only ports that are never opened in the firewall. Every module reads from this namespace: to set the port a service listens on, to tell nginx where to proxy, and to declare which ports the firewall should open.

networking.firewall.allowedTCPPorts = with config.homeserver.ports; [ portA portB ];

04 Module management

One service per file

Each file is fully self-contained: users, systemd unit, firewall rules, state directories, and secrets injection all live in the same file. Never group unrelated services together — it makes each service independently patchable and upgradeable.

Internal structure

Follow this order within a module file:

{ config, pkgs, lib, ... }:
{
  # User/group (custom services only)
  users.groups.myapp = { };
  users.users.myapp  = { isSystemUser = true; group = "myapp"; };

  # Service declaration
  services.myapp = { ... };

  # Systemd overrides (sandbox, EnvironmentFile)
  systemd.services.myapp.serviceConfig = ...;

  # Firewall
  networking.firewall.allowedTCPPorts = with config.homeserver.ports; [ myapp ];
}

External flake dependencies

Some services depend on a third-party flake input rather than a nixpkgs package. These are declared in flake.nix as inputs and passed via specialArgs — the module then self-imports the external NixOS module. This keeps the flake module list as purely local file paths.

05 Logging

Pipeline

All logging is localhost-only. No external log shipping.

journald  →  Promtail (9080)  →  Loki (3100)  →  Grafana (3010)

Promtail reads from __journal__ (the systemd journal socket), enriches each entry with labels, and pushes to Loki. Grafana queries Loki and renders dashboards. Loki and Promtail ports are not opened in the firewall — they are unreachable outside localhost.

Every log entry carries these labels. Grafana dashboards cascade-filter on them.

Retention policy

Loki applies tiered retention. Lower-noise entries are kept for shorter periods; errors and warnings are kept longest.

SelectorRetention
level=info, category=system1 day
level=info, service=<high-volume>2 days
level=info7 days
level=notice7 days
level=warning14 days
all other (err, crit, emerg, alert)30 days

Compactor runs with a 2-hour delete delay. Retention is enforced at the stream level — selectors are evaluated in priority order; the highest matching priority wins.

Dashboards

Both dashboards are provisioned as code from modules/nixos-stable/grafana.nix — no manual Grafana configuration needed after a rebuild.

DashboardPurpose
Homeserver LogsFull log stream. Cascade variable filters: Category → Module → Service → Level. Refreshes every 30 s. Default window: last 1 h.
Homeserver AlertsTable of error/critical counts by category, module, and service over the selected range. Each row links directly to the Logs dashboard filtered to that service and error levels.

Adding a new service to Promtail

When a new module is added, its systemd unit must be registered in modules/nixos-stable/promtail.nix so it gets the correct category and module labels. Without this it falls back to category=system, module=unknown.

Module folderRules groupWhat to add
nixos-stable/rulesNixosStableAdd service name to the alternation regex
nixos-unstable/rulesNixosUnstableAdd service name to the alternation regex
containers-podman/rulesContainersOnly needed if unit does not follow podman-<name>.service pattern
services/rulesServicesAdd service name to the alternation regex

If the unit name needs a clean service label (e.g. phpfpm-nextcloud → nextcloud), add an explicit override rule in the same group following the existing pattern.

06 Patching & upgrades

Edit and validate workflow

The live config at /etc/nixos/ is root-owned. All edits go through the mirror first:

  1. Verify mirror is in sync with live config: rsync -a --exclude='.git' --exclude='apps/' /etc/nixos/ /home/kryt/nixos-mirror/
  2. Edit files in /home/kryt/nixos-mirror/
  3. Build from the mirror to catch all eval and build errors without touching the live system: nixos-rebuild build --flake /home/kryt/nixos-mirror#homeserver
  4. Copy changed files to /etc/nixos/
  5. Activate for testing (no boot default change): sudo nixos-rebuild test --flake /etc/nixos#homeserver
  6. If test looks good, make permanent: sudo nixos-rebuild switch --flake /etc/nixos#homeserver
  7. Commit and optionally tag: git tag working-YYYY-MM-DD

Flake lock updates

Bumps all inputs — stable channel rolls forward, unstable overlay picks up new package versions:

sudo nix flake update /etc/nixos

After updating the lock, always follow the full edit/validate workflow above. Pay attention to packages in the unstable overlay — they may require data migrations or config changes between versions.

Nextcloud upgrades Nextcloud only supports single-version upgrades. If the lock update skips a major version, the service will fail to start with a migration error. Restore from backup and upgrade incrementally.

Podman container digests

Podman containers are pinned by digest in their module files — they never auto-update. To upgrade:

  1. Pull the new image: podman pull <image>:<tag>
  2. Get the digest: podman inspect --format '{{.Digest}}' <image>:<tag>
  3. Update the digest in the module file in nixos-mirror/
  4. Build, test, and switch

Rolling back

Roll back to the previous generation without touching git:

sudo nixos-rebuild switch --rollback

Roll back to a tagged stable state:

sudo git -C /etc/nixos checkout <tag>
sudo nixos-rebuild switch --flake /etc/nixos#homeserver

Nix garbage collection

Automatic weekly GC deletes generations older than 14 days. To run manually:

sudo nix-collect-garbage --delete-older-than 14d

Check store size: du -sh /nix/store. Each generation pinned by a tag or a git ref keeps its closure alive until the ref is removed.
